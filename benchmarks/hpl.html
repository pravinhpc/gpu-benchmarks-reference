HPL / LINPACK

The benchmark that ranks the world's fastest supercomputers — dense linear algebra at full-system scale, still the standard GPU cluster acceptance test — updated 2026-09-07.

1. What is HPL, and why does it matter?

HPL (High-Performance Linpack) traces back to the LINPACK software package created in the 1970s-80s by Jack Dongarra and colleagues at Argonne National Laboratory / University of Tennessee. HPL, the modern parallel variant introduced in the 1990s, generates a dense n×n linear system Ax=b, solves it via LU factorization with partial row pivoting followed by triangular solves — roughly (2/3)N³ FLOPs total.

Why it's important

  • The TOP500 standard — HPL has ranked the world's fastest supercomputers since 1993. Every major system's public reputation rests on this one number.
  • Full-system stress test — sustaining near-peak FLOPS across an entire cluster for an extended run stresses power delivery, cooling, and interconnect simultaneously. A cluster that can't hold near-peak HPL performance for the full run duration usually has a real hardware or power/thermal issue — which is exactly why it's still used for GPU cluster acceptance testing today, criticism notwithstanding.
  • Widely criticized, still standard — HPL is almost purely compute-bound and doesn't reflect real HPC/AI application performance well (this criticism is exactly why HPCG was created — see §4). Despite that, it remains the universal reference point because it's been consistent since 1993.

What it's used for

  • TOP500 list submissions (public bragging rights + procurement validation)
  • New GPU cluster acceptance testing — proving a cluster sustains near-peak FLOPS at full scale before handoff
  • Power/cooling/interconnect stress testing under sustained maximal load
  • Customer validation deliverables — real-world runs are used as procurement/acceptance evidence

2. How it runs (algorithm)

HPL processes the matrix in panels: each step does a panel factorization (LU decomposition of a column block) followed by a trailing matrix update (applying that transformation to the remaining unfactored submatrix via large GEMM operations). The trailing-matrix-update dominates and is O(n³) FLOPs against O(n²) data movement — high arithmetic intensity is exactly why HPL can sustain a large fraction of theoretical peak, unlike memory-bound codes (contrast with HPCG, §4).

NVIDIA's GPU-accelerated HPL is distributed via the nvcr.io/nvidia/hpc-benchmarks NGC container. GPUs handle the compute-heavy trailing matrix update (large GEMMs); CPUs typically handle panel factorization and pivoting logistics — the split is tuned via NB (§3). Source: glennklockwood.com HPL, NVIDIA HPL Benchmark docs.

3. HPL.dat tuning parameters

NOrder of the coefficient matrix (problem size)Large enough to fill ~80-90% of available memory — too small under-stresses the system and gives a misleadingly low efficiency number. General guidance: GPU benchmarking should target ~90% of memory vs. 70-80% for CPU-only runs.
NBPartitioning block sizeGPU HPL typically uses much larger NB (256–1024) than CPU-only HPL (128–256), tuned to the GPU's own GEMM tile size.

4. Test variants — HPL vs HPL-AI/HPL-MxP vs HPCG

VariantPrecisionWhat it measuresWhy run it
HPLFP64 (double)Pure dense-matrix compute throughputThe TOP500-ranking standard; validates raw FLOPS + full-system stability under sustained compute load.
HPL-AI / HPL-MxPMixed precision (low-precision LU factorization + GMRES-based iterative refinement to reach FP64-equivalent accuracy)Exploits Tensor Cores for much higher raw FLOPS while still validating to FP64 accuracyShows HPC/AI convergence — what a system can do leveraging the same low-precision hardware paths used for AI training/inference. NVIDIA's HPL-MxP (in the hpc-benchmarks container) is understood to be the same research lineage/successor to "HPL-AI" (same Dongarra/Luszczek group, same technique) — not explicitly confirmed as an official rename, flagged rather than asserted.

You run more than one because HPL alone can make a system look better than it performs on real applications — HPCG is the standard complement that catches that gap, and HPL-MxP shows AI-relevant mixed-precision throughput. Source: HPCG benchmark (Wikipedia), Dongarra & Heroux HPCG paper, arXiv:2509.19618 (HPL-MxP paper).

5. How results are measured

Rmax

Achieved performance (measured, in FLOP/s) — the official TOP500 ranking number.

Rpeak

Theoretical peak performance of the full system (sum of every core/GPU's peak FP64 FLOPS).

Nmax

The problem size (N) used to achieve Rmax.

Efficiency = Rmax / Rpeak (as a percentage) is the standard way to judge how well a system/tuning realizes its theoretical potential. Typical "well-tuned" GPU cluster efficiency is cited in the 78-90% range across several sources — but real published flagship numbers (§6) often land lower than that, so treat 78-90% as an upper-bound aspiration, not a guarantee.

9. How to run it

Get the container

docker pull nvcr.io/nvidia/hpc-benchmarks:25.04
# Sample HPL.dat files ship inside at:
#   /workspace/hpl-linux-x86_64/sample-dat/       (x86)
#   /workspace/hpl-linux-aarch64-gpu/sample-dat/  (Grace/ARM)

Example Slurm launch (8 nodes × 8 GPUs = 64 GPUs)

srun -N 8 --ntasks-per-node=8 --cpu-bind=none --mpi=pmix \
  --container-image="${CONT}" \
  ./hpl.sh --dat /workspace/hpl-linux-x86_64/sample-dat/HPL-64GPUs.dat \
  --gpu-affinity --cpu-affinity --mem-affinity --ucx-affinity

The hpl.sh wrapper's affinity flags matter — misbinding to the wrong NUMA node/GPU directly kills efficiency.

Interpreting output

HPL prints, per (N, NB, P, Q) combination tested: wall-clock Time, achieved GFLOPS, and a PASSED/FAILED residual check verifying numerical correctness. A FAILED result means the run doesn't count, regardless of how fast it was.

Common pitfalls

  • N too small — doesn't fill memory or run long enough to reach steady-state performance; gives an artificially low, non-representative efficiency number.
  • Wrong P×Q grid — a badly-shaped grid (far from square, or mismatched to physical network topology) kills scaling; use the calculator in §7.
  • NB mismatched to GPU tile size — using CPU-typical NB values (128-256) on a GPU run leaves performance on the table.

LAMMPS, GROMACS & NAMD

Real molecular-dynamics application benchmarks — the "does a real scientific app actually run fast" complement to HPL/HPCG — updated 2026-09-09.

1. What are these, and why do they matter together?

LAMMPS

Sandia National Labs. General-purpose classical MD — materials science, granular flow, coarse-grained systems. Highly extensible.

GROMACS

University of Groningen. Biomolecular MD — proteins, membranes, nucleic acids. The dominant tool in pharma/structural biology.

NAMD

University of Illinois (Beckman Institute). Biomolecular MD built for massive parallel scalability — originally for supercomputers, virus-capsid-scale simulations.

They're grouped as the "real HPC application" category alongside HPL/HPCG (see the HPL page) because they measure actual scientific-workload throughput — nanoseconds of simulated time per day — not synthetic FLOPS. Pharma companies, national labs, universities, and cloud HPC offerings (AWS/Azure/GCP HPC instance marketing) all use these results as real procurement evidence.

2. GPU acceleration approach

LAMMPS

Two competing packages: GPU package (partial offload — pairwise force calc only) vs. KOKKOS package (whole simulation on GPU, minimizes host↔device transfer). Real finding: Kokkos "outscales the GPU package because it minimizes host-to-GPU data transfer" (ACES cluster study, H100 vs Intel Data Center GPU Max 1100). CPU-GPU ratio: 16-32 CPU cores per GPU.

GROMACS

Native CUDA/SYCL/OpenCL. Default hybrid scheme still runs PME and bonded forces on CPU — full offload requires explicit flags (-nb gpu -pme gpu -bonded gpu -update gpu), which "pins threads to host CPU."

NAMD

GPU-resident mode (NAMD 3.0+) keeps simulation data on-device between timesteps, eliminating per-step host-device communication — claimed >2× performance gain over the earlier GPU-offload mode, up to 7× on supported hardware (DGX) vs. the old mode.

Universal bottleneck across all three: PME/electrostatics (particle-mesh Ewald) — usually the hardest part to offload efficiently and the first thing to check when GPU scaling disappoints.

3. Key config parameters

ToolFlagsNotes
GROMACS-nb gpu -pme gpu -bonded gpu -update gpuFull offload. Also: -ntmpi/-ntomp (thread/rank split), -pin on -pinstride 1 (CPU pinning — matters a lot for performance).
LAMMPS-sf gpu or -sf kk -k on g <N>GPU package vs. Kokkos (N = number of GPUs). Minimum optimal single-GPU load: 64×32,000 atoms (LJ), 128×32,000 (EAM), 16×32,000 (Rhodopsin).
NAMD+devices <list>GPU selection. GPU-resident mode is a build/runtime mode switch, not a per-flag toggle.

4. Standard benchmark systems

LAMMPS

5 standard problems, each 32,000 atoms, 100 timesteps: LJ (Lennard-Jones fluid), Chain (polymer melt), EAM (Cu metallic solid), Chute (granular flow), Rhodo (rhodopsin protein in lipid bilayer, CHARMM force field, PPPM electrostatics).

GROMACS

No single "standard," but the NHR@FAU 2024.1 study used 6 real systems: 20,248 → 1,066,628 atoms (R-143a in hexane, RNA+water, membrane protein, protein in water, protein membrane channel, virus protein). AMD's own benchmarks use the ADH dodecahedron system.

NAMD

DHFR (23,558 atoms), ApoA1 (92,224 atoms), STMV (1,066,628 atoms — satellite tobacco mosaic virus, the large-scale flagship benchmark).

Source: docs.lammps.org/Speed_bench.html, ks.uiuc.edu/Research/namd/benchmarks.

5. How results are measured

Standard metric: ns/day (nanoseconds of simulated time per wall-clock day). Higher = faster. No universal "good" threshold — depends entirely on system size (smaller systems → much higher ns/day, since less work per timestep).

8. How to run

GROMACS (most complete example)

gmx mdrun -v -s benchmark.tpr -nb gpu -pme gpu -bonded gpu -update gpu \
  -ntmpi 1 -ntomp 16 -pin on -pinstride 1 -nsteps 200000 -deffnm benchmark_name

Output: ns/day printed directly in the mdrun log/performance summary — higher is better, compare against published reference numbers (§6) for the same system size.

LAMMPS

# Kokkos GPU mode (general pattern — see docs.lammps.org/Speed_kokkos.html for exact flags)
lmp -sf kk -k on g <N> -pk kokkos -in in.rhodo

NAMD

# GPU-resident mode requires a NAMD 3.0+ build; GPU selection via:
namd3 +devices 0,1,2,3 +p32 apoa1.namd

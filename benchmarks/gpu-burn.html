gpu-burn & DCGM Diagnostics

GPU stress-test and burn-in tooling — compute+thermal+correctness stress before a card or node enters production — public reference, compiled 2026-09-07.

1. What is gpu-burn, and why does it matter?

gpu-burn (github.com/wilicc/gpu-burn, 2.3k stars, BSD-2-Clause) is Ville Timonen's original GPU stress-test tool — wilicc on GitHub is the original author, this is not a third-party fork. Released 2013. It forks one process per GPU, allocates a high percentage of GPU memory, and runs continuous cuBLAS matrix multiplications for a specified duration — while periodically validating results against a reference computation to catch silent data corruption (SDC), not just "does it run."

Why it matters

  • Pre-deployment burn-in — catches thermal throttling, marginal power delivery, and unstable/defective cards before they enter production.
  • Catches silent data corruption — a GPU that runs hot but computes wrong answers is worse than one that visibly crashes; gpu-burn's correctness check is what catches this.
  • A real production workflow, not just a one-time test — commonly run on a regular cadence and before returning repaired nodes to service.

Where it fits alongside NCCL & HPL

  • gpu-burn — single/multi-GPU compute + thermal + correctness stress (this page)
  • NCCL tests — interconnect/fabric health (ring/tree AllReduce busbw)
  • HPL — full-system sustained FLOPS at scale (power/cooling/interconnect combined)
  • Different scope, same goal: prove the hardware is production-ready before it's trusted with real workloads.

2. How it runs

Default precision is double (DGEMM) via -d — heavier thermal/power load, closer to worst-case realistic stress than single-precision. Runs on all visible GPUs simultaneously by default; -i N narrows to one GPU.

3. CLI flags

FlagMeaning
-m XAllocate X megabytes of GPU memory
-m N%Use N percent of available GPU memory
-dUse doubles (DGEMM instead of SGEMM) — heavier thermal/power load
-tcAttempt to use Tensor Cores (v1.1+, if hardware supports it)
-c FILEUse FILE as the compare kernel (default: compare.ptx)
-lList all GPUs detected in the system
-i NRun the test exclusively on GPU N
-hDisplay help
[TIME]Trailing positional argument — duration to run, in seconds

Build via make, with COMPUTE=, CUDAPATH=, NVCCFLAGS= for multi-arch targeting (e.g. -gencode=arch=compute_90,code=sm_90 for Hopper).

4. Test variants

Standard (SGEMM)

Default precision. Lighter load than DGEMM.

Double-precision (-d, DGEMM)

The heaviest thermal/power load — closest to worst-case realistic stress. Most commonly used for real burn-in.

Tensor Core (-tc)

Uses Tensor Cores where supported (v1.1+) — stresses a different compute path than standard CUDA cores.

No distinct "quick smoke test" mode exists — duration is just the trailing seconds argument. In practice: short runs (60-300s) for smoke tests, multi-hour runs for real pre-production burn-in. No official NVIDIA NGC container was found for gpu-burn — only community/self-built Docker images from the repo's own Dockerfile.

5. How results are measured

Real sample output (sourced):

# Single GPU
89.4%  proc'd: 2916 (2015 Gflop/s)   errors: 0   temps: 86 C

# Multi-GPU
11.7%  proc'd: 2947 (7124 Gflop/s) - 2664 (6963 Gflop/s)   errors: 0 - 0   temps: 56 C - 73 C
FieldMeaning
Load %Progress through the current test cycle
proc'dNumber of matrix operations processed
Gflop/sAchieved throughput — the headline performance number
errorsMust be 0. Nonzero = correctness failure detected by the compare-vs-reference check — a real computational error under stress, not a crash. Flag the GPU for RMA.
tempsPer-GPU temperature during the run — watch for thermal throttling

Final summary reports OK vs. FAULTY per GPU.

Honest gap: no sourced GFLOPS reference ranges for V100/A100/H100 specifically were found in this research pass — don't treat the sample numbers above as expected values for any particular GPU generation; they're just real example output.

6. DCGM Diagnostics — NVIDIA's official complement

DCGM Diagnostics (dcgmi diag, part of NVIDIA's Data Center GPU Manager, running NVVS underneath) is NVIDIA's own official stress-test/diagnostic tool — more tiered and more deeply documented internally than gpu-burn. Common practice pairs both: DCGM -r 3 as the acceptance gate + gpu-burn as a complementary compute/correctness stress tool, with -r 1 wired into the scheduler as job prologue/epilogue.

Diagnostic levels — real timing data (8-GPU system)

Example commands

# Quick pre-job sanity check (seconds)
dcgmi diag -r 1

# Standard acceptance gate (tens of minutes)
dcgmi diag -r 3

# Full diagnostic including HBM pattern testing (hours)
dcgmi diag -r 4

# Extended User Diagnostics — full run (9-10 hours)
dcgmi diag -r eud -p "eud.passthrough_args='gpu_diag'"

# EUD p0only variant (~2 hours)
dcgmi diag -r eud -p "eud.passthrough_args='gpu_diag_p0only'"

Source: NVIDIA DCGM Diagnostics docs, github.com/NVIDIA/DCGM.

8. How to run it

Build from source

git clone https://github.com/wilicc/gpu-burn.git
cd gpu-burn
make

Docker

docker build -t gpu-burn .
docker run --rm --gpus all gpu-burn

Example runs

# Quick smoke test — 60 seconds, default precision
./gpu_burn 60

# Real burn-in — 1 hour, double precision (heaviest load)
./gpu_burn -d 3600

# Target a specific GPU
./gpu_burn -i 0 -d 3600

# List detected GPUs first
./gpu_burn -l

Runs on all visible GPUs simultaneously by default (one forked process per GPU). Watch the periodic output lines (§5) — errors must stay at 0 for the whole run; temps should stabilize, not climb continuously (continuous climb = thermal throttling / inadequate cooling).

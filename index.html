1. What is Nemotron, and why does it matter?

Nemotron is NVIDIA's family of open large language models (LLMs) — spanning base/foundation models, instruction-tuned chat models, reward models, reasoning models, vision-language models, and hybrid Mamba-Transformer architectures. It is NVIDIA's flagship demonstration of the full NeMo software stack: data curation → pretraining → alignment (SFT/DPO/RLHF/RLVR) → evaluation → optimized inference (TensorRT-LLM / vLLM / NIM).

Why it's important

  • Openness: weights, and increasingly training data (e.g. Nemotron-CC, Nemotron-Post-Training-Dataset) and reasoning traces are released — unusual for a frontier-adjacent lab, aimed at enterprise/sovereign-AI customers who need auditable, customizable models.
  • Reference architecture: proves out NVIDIA's own tools (NeMo Framework, NeMo Curator, NeMo Aligner/RL, Megatron-Bridge, NIM, TensorRT-LLM) end-to-end — what NVIDIA sells to enterprises, NVIDIA uses on itself first.
  • Efficiency leadership: Nemotron-H and Nemotron-Nano use hybrid Mamba2/Transformer blocks for much cheaper long-context inference than pure-attention models of similar quality.
  • Customization-first: designed to be fine-tuned/distilled by customers (enterprises, CSPs, NCPs) for domain use cases — not just used as-is.
  • Commercial flywheel: distributed via build.nvidia.com, NIM microservices, and inference-provider/CSP partners — drives GPU consumption for both training and inference.

What it's used for

  • General chat / instruction following (Nemotron-Instruct)
  • Agentic reasoning & tool use (Nemotron Nano/Super/Ultra reasoning models)
  • Reward modeling for RLHF pipelines (Nemotron-Reward)
  • Synthetic data generation (SDG) for training other models
  • Document parsing / OCR (Nemotron-Parse)
  • RAG & retrieval (embeddings/rerankers in the Nemotron/NeMo Retriever family)
  • Domain fine-tuning by customers (e.g. enterprise NL→query-language use cases)

D. Fine-tune / customize

  1. Establish baseline: run OOTB Nemotron on your target benchmark/eval set.
  2. Identify capability gap → decide SFT (LoRA/full) vs DPO vs RLVR vs distillation based on the "learning signal" you have (labeled data, pairwise preferences, verifiable success, or a teacher model).
  3. Pick framework: AutoModel for broad/easy day-0 support at <1000 GPUs; Megatron-Bridge for max throughput at >1000 GPUs.
  4. Generate synthetic data if scarce (NeMo Data Designer) or apply privacy protection (NeMo Safe Synthesizer) if handling sensitive data.
  5. Train (NeMo RL / NeMo Customizer microservice for a single-API-call path).
  6. Re-run the same benchmark to measure improvement; validate on real-world task before shipping.
Reasoning-model specific gotcha: agentic/coding harnesses that don't support custom request flags (e.g. Cursor) can mis-parse "thinking" vs normal output if the closing think-tag is malformed — check for a runtime reasoning-parser flag / updated vLLM·TRT-LLM·SGLang build before benchmarking coding-agent tasks on Nemotron Super/Ultra.

1. What is Megatron-LM / Megatron-Core, and why does it matter?

Megatron-LM began as NVIDIA Research's 2019 paper "Training Multi-Billion Parameter Language Models Using Model Parallelism" (arXiv:1909.08053) — the first practical tensor parallelism scheme for transformers: an intra-layer model-parallel split implementable with a handful of communication ops inserted into native PyTorch, no compiler or custom library required.

Today it's three related things:

Megatron-LM

The reference implementation repo — pre-configured training scripts, research/experimentation focus. Where new techniques land first.

Megatron-Core

A composable library of GPU-optimized building blocks (attention, transformer layers, norm layers, embeddings, activation recomputation, distributed checkpointing) — the productized core that NeMo Framework and other stacks build on.

Megatron-Bridge

HF ↔ Megatron checkpoint conversion + production training recipes, hosted under the NVIDIA-NeMo GitHub org.

Why it matters

  • Origin point of practical tensor parallelism — the technique nearly every subsequent large-scale training framework (DeepSpeed, FSDP-based stacks, JAX/Pax) either uses directly or was directly inspired by.
  • The stack NVIDIA trains its own models on — Nemotron (see the Nemotron reference) is trained via NeMo Framework, which is built on Megatron-Core underneath.
  • Where 5D parallelism composability lives — tensor, pipeline, data, sequence, context, and expert parallelism aren't separate tools; Megatron-Core composes all of them into one coherent training loop.

What it's used for

  • Pretraining dense and MoE LLMs from scratch at scale (2B → 462B+ params, thousands of GPUs)
  • Continued pretraining and SFT on existing checkpoints
  • Reference benchmark for MLPerf Training submissions
  • Research vehicle for new parallelism/memory techniques before they land in production frameworks

2. How it runs — the 5D parallelism

A Megatron training job's total GPU count decomposes as TP × PP × CP × EP × DP. Each dimension solves a different scaling problem, and they compose rather than compete.

The six dimensions

  • Tensor Parallelism (TP) — splits individual weight matrices across GPUs; use for large hidden dims (4096+). Pair with Sequence Parallelism. Best within a node (NVLink).
  • Sequence Parallelism (SP) — shards the sequence dimension in LayerNorm/Dropout (the non-TP regions) to cut activation memory. Flag: --sequence-parallel. Enable whenever using TP.
  • Pipeline Parallelism (PP) — splits layers vertically by depth across GPUs; best for very deep models (50+ layers). Interleaved/virtual scheduling improves throughput 10%+ at comparable memory.
  • Context Parallelism (CP) — splits long sequences (8K+ tokens) across GPUs for attention. Dynamic CP (new 2026) gives up to 1.48× speedup for variable-length sequence training.
  • Expert Parallelism (EP) — distributes MoE experts across GPUs; must enable Sequence Parallelism when combined with TP.
  • Data Parallelism (DP) — standard full-replica DDP, or FSDP with three sharding levels (optim=ZeRO-1, optim_grads=ZeRO-2, optim_grads_params=ZeRO-3).

5. How results are measured — MFU

Model FLOPs Utilization (MFU) is the standard efficiency metric: actual achieved FLOPs / peak theoretical FLOPs of the hardware. It's reported alongside tokens/sec and step time, but MFU is what lets you compare efficiency across totally different model sizes and cluster scales on equal footing.

Why MFU rises with model size

Larger GEMMs have higher arithmetic intensity (more FLOPs per byte moved) — Megatron-LM's own README reports MFU rising from 41% to 47-48% as model size scales 2B→462B on H100 clusters.

Why MFU falls with GPU count

Communication becomes increasingly exposed (not fully overlapped with compute) as scale grows — the same README reports 47%→42% MFU when scaling from 96 to 4,600+ GPUs.

Source: NVIDIA/Megatron-LM README.

1. What is NCCL, and why does it matter?

NCCL ("Nickel") is NVIDIA's library of topology-aware, optimized primitives for multi-GPU and multi-node collective communication: AllReduce, AllGather, Broadcast, Reduce, ReduceScatter, plus arbitrary point-to-point Send/Recv patterns (which compose into AllToAll, scatter, gather). It runs across PCIe, NVLink, NVSwitch, InfiniBand, and Ethernet/RoCE, in single- or multi-process (MPI/Slurm) contexts.

Why it's important

  • The actual ceiling on training throughput at scale. Every distributed training framework (Megatron-LM, NeMo, PyTorch DDP/FSDP, DeepSpeed) calls into NCCL for cross-GPU gradient/activation communication. Compute (TFLOPs) is rarely the bottleneck at 1000+ GPU scale — communication is.
  • Cluster health gatekeeper. NCCL AllReduce bandwidth is the standard "does this fabric actually work" test for new/repaired nodes before they're released back into a production cluster — a topology or cabling fault that doesn't break connectivity can still tank NCCL bandwidth.
  • Topology-aware by design: automatically discovers and exploits NVLink/NVSwitch domains, PCIe trees, and IB/RoCE fabric shape, rather than treating all GPUs as uniformly reachable.
  • Foundational, not optional: works alongside MPI (MPI often orchestrates ranks/processes; NCCL does the GPU-to-GPU data movement) — used together in virtually every large training job.

What it's used for

  • Data-parallel gradient AllReduce (the classic distributed-training use case)
  • Tensor/pipeline/expert-parallel communication in Megatron-Core-style model parallelism
  • New-cluster acceptance testing & ongoing node health validation (NCCL busbw as the pass/fail signal)
  • Debugging fabric issues: a bad cable, mis-seated NVLink bridge, or misconfigured IB routing shows up as a busbw regression before it shows up as a training crash

2. How it runs (architecture)

At init, NCCL builds a topology graph of the system — reading /var/run/nvidia-topologyd/virtualTopology.xml if present, or probing PCIe/NVLink directly (the same graph nvidia-smi topo -m shows: NV#=NVLink hops, PXB/PHB/PIX=PCIe distance classes, SYS=cross-socket/QPI). From that graph it selects, per collective and per message size, an algorithm, a protocol, and a channel count.

Algorithms

  • Ring — bandwidth-optimal, every link carries equal load; best for small/medium node counts.
  • Tree — fewer hops (lower latency), unequal link load; wins as node count grows and latency starts to dominate over bandwidth.
  • CollNet / CollNetDirect / CollNetChain — offloads the reduction itself into the IB switch ASIC via SHARP (Scalable Hierarchical Aggregation and Reduction Protocol).
  • NVLS (NVLink SHARP) — reduction offloaded into the NVSwitch fabric itself; needs 3rd-gen+ NVSwitch (Hopper/Blackwell NVLink4). NVLSTree combines NVLS intra-node with Tree inter-node.
  • PAT — newer large-scale algorithm alongside Ring/Tree/NVLS/CollNet in current NCCL versions.

Protocols (per-channel wire format)

  • Simple — highest bandwidth, higher per-step latency (memory-fence based sync).
  • LL (Low-Latency) — flag-based sync instead of memory barriers; lower bandwidth, much lower latency; good for small messages.
  • LL128 — LL variant tuned for NVLink at 128-byte granularity; good middle ground, only on platforms that support it.

Transport underneath: IB Verbs, libfabric (via OFI plugins), or TCP sockets — with GPUDirect RDMA letting the NIC read/write GPU memory directly when PCIe topology allows, bypassing the CPU/host memory copy.

Multi-Node NVLink (MNNVL) — a third topology class

Everything above assumes the classic split: NVLink/NVSwitch inside a node, IB/RoCE between nodes. GB200 NVL72-class systems (already cited in §5/§6) break that assumption — Multi-Node NVLink (MNNVL) extends the NVLink domain itself across physical nodes: up to 72 GPUs (36 Grace CPU nodes) sit in one single NVLink domain, not 9 separate 8-GPU NVSwitch domains stitched together over IB.

Single-node NVSwitch

8 GPUs, one NVSwitch domain. All-to-all NVLink bandwidth within the node; anything beyond the node goes over IB/RoCE.

Traditional multi-node

Many 8-GPU NVSwitch domains connected by IB/RoCE. Two distinct fabrics, two very different bandwidth tiers (NVLink ≫ IB).

MNNVL (GB200 NVL72)

Up to 72 GPUs in one NVLink domain spanning multiple physical nodes/trays. Requires the IMEX (Internal Memory EXport) service to export/import GPU memory across separate OS/node boundaries within the same NVLink domain.

Reliability tradeoff worth knowing: because MNNVL puts up to 72 GPUs in a single NVLink domain, a single bad GPU, NVLink bridge, or optical cable can degrade or take down communication for the entire 72-GPU domain — not just the node it's physically in. Factor this into cluster acceptance testing for GB200 NVL72-class systems — it's more failure-sensitive than testing traditional 8-GPU nodes independently.

Channels — how NCCL uses multiple SMs per collective

NCCL doesn't run a collective as one monolithic operation — it splits the buffer into disjoint chunks and processes them across multiple channels, each running as its own CUDA block on its own streaming multiprocessor (SM). This is the mechanism that lets a single AllReduce call actually use many SMs in parallel instead of bottlenecking on one.

  • NCCL_MIN_NCHANNELS / NCCL_MAX_NCHANNELS (§3) set the floor/ceiling on channel count; the hard ceiling is 32 channels as of NCCL 2.5+.
  • More channels = more parallelism for the collective, but each channel occupies an SM that's then unavailable to the actual compute kernels (matmuls, attention, etc.) running alongside it in the same training step — a real resource contention, not just a theoretical one.
  • Manual channel-count tuning is now generally discouraged — NCCL's automatic selection based on message size and detected topology outperforms most hand-tuning in current versions; treat NCCL_MIN/MAX_NCHANNELS as a debugging lever, not a default-path tuning knob.

Topology detection internals — reading and dumping the graph

The nvidia-smi topo -m matrix — already referenced throughout this page — uses these codes, ranked roughly best→worst for GPU-to-GPU or GPU-to-NIC affinity:

CodeMeaning
XSelf (diagonal entry)
NV#NVLink connection, where # = number of bonded links (e.g. NV18 = full-bandwidth NVSwitch-connected pair). Fastest class by far.
PIXSame PCIe switch, ≤1 bridge hop
PXBMultiple PCIe bridges, but no Host Bridge (CPU) crossing
PHBSame PCIe Host Bridge (same CPU socket)
NODESame NUMA node, but different PCIe bridges

Ranking: NV# ≫ PIX > PXB > PHB > NODE > SYS. This is exactly the distance scale NCCL_P2P_LEVEL and NCCL_NET_GDR_LEVEL (§3) are expressed in.

NCCL builds its topology graph once at communicator init, either by probing PCIe/NVLink directly or by loading NCCL_TOPO_FILE (default /var/run/nvidia-topologyd/virtualTopology.xml if present). You can capture what NCCL actually detected with NCCL_TOPO_DUMP_FILE=/path/to/topo.xml — useful for diffing "what NCCL sees" against "what the hardware actually is" when debugging a suspected topology misdetection. For MNNVL systems, note that NCCL_TOPO_FILE should contain only the single-node topology even though NCCL_TOPO_DUMP_FILE captures the full multi-node NVLink domain.

Honest gap: NCCL's internal graph-search algorithm — exactly how it scores and selects candidate ring/tree channel orderings over the detected topology — is not publicly documented, including in the most detailed academic treatment available (arXiv:2507.04786, "Demystifying NCCL"), which describes that rings/trees are computed once at init and reused, but not the scoring heuristic itself. Don't trust any source (including this one) that claims to fully explain the search algorithm — the honest answer is: NCCL computes and caches channel assignments at init based on the topology graph, and the exact path-scoring logic is internal/undocumented.

5. nvbandwidth — raw link bandwidth, not collective bandwidth

nvbandwidth is NVIDIA's open-source tool for measuring raw point-to-point memcpy bandwidth across individual links (PCIe, NVLink) — via either the Copy Engine (CE) or an SM/kernel-based copy. It sits one layer below nccl-tests: nvbandwidth has no collective-algorithm overhead (no ring/tree construction, no protocol selection) — it's the closest thing to a hardware bandwidth ceiling test.

nvbandwidth vs nccl-tests — the standard diagnostic split:
  • nvbandwidth = what the raw link can physically deliver (PCIe/NVLink ceiling)
  • nccl-tests = what the collective operation actually achieves against that ceiling
If nccl-tests shows poor AllReduce bus-bandwidth but nvbandwidth shows expected NVLink/PCIe numbers on the same links, the problem is algorithmic/software (tuning, topology detection, protocol selection). If nvbandwidth itself shows degraded raw numbers, it's a hardware/topology/link problem (bad NVLink, PCIe misconfiguration, wrong GPU affinity) — check this before chasing NCCL tuning flags.

What it tests

  • Host-to-Device / Device-to-Host transfers (PCIe)
  • Device-to-Device transfers over NVLink or PCIe (CE or SM copy method)
  • Bidirectional simultaneous transfers
  • All-to-all / multi-pair topology sweeps
  • Multi-node tests (build with -DMULTINODE=1, MPI-based — one rank per GPU)

CLI usage

./nvbandwidth                                    # run all testcases
./nvbandwidth -l                                 # list available testcases
./nvbandwidth -t device_to_device_memcpy_write_ce # run by name or index
./nvbandwidth -p device_to_device                # run by prefix match
./nvbandwidth -b 512                             # buffer size in MiB (default 512)
./nvbandwidth -i 3                               # test iterations/samples
./nvbandwidth -s                                 # skip data verification
./nvbandwidth -j                                 # JSON output
./nvbandwidth -v                                 # verbose

Other flags: -d disable CPU affinity, -m use mean instead of median. Verify exact flag spelling against the current README before scripting — flags have shifted slightly across releases.

6. How results are measured / interpreted

Every test reports two bandwidth numbers per message size:

algbw (algorithm bandwidth)

size / time — the naive number. Not comparable across different rank counts, because the same collective moves different total bytes depending on how many ranks participate.

busbw (bus bandwidth)

algbw × correction factor — normalized to actual hardware bytes moved, so it's directly comparable to the physical link's peak bandwidth regardless of rank count. This is the number you judge fabric health against.

Rail-optimized topology — why NCCL_IB_HCA rail/plane syntax exists

§3 already documents the NCCL_IB_HCA=<hca>[:<port>[:<rail>[:<plane>]]] syntax and NCCL_CROSS_NIC — this is the topology those exist for. Modern 8-GPU nodes (H100/GB200-class) commonly use a rail-optimized network design: each of the 8 GPUs connects to a different leaf switch (rail 0 through rail 7) instead of all 8 sharing one shared leaf switch. The result: GPU 0 on every node in the cluster shares a leaf switch with every other node's GPU 0, GPU 1 shares a different leaf switch with every other node's GPU 1, and so on.

Why this matters operationally: it lets same-rank collectives (e.g. all the "GPU 0" ranks across a job) communicate through a single switch hop instead of crossing the spine — lower latency, more predictable bandwidth. It's also why NCCL_CROSS_NIC exists: letting a ring/tree freely hop between rails defeats the locality this design buys you, so NCCL defaults to keeping each channel on one rail where possible. And it's why NCCL_IB_HCA's rail/plane addressing exists — to let you pin traffic to the correct rail when auto-detection picks wrong (e.g. a management NIC instead of a compute-fabric rail).

RoCE v2 vs InfiniBand

The real differentiator isn't peak bandwidth — modern RoCEv2 and IB can reach comparable numbers with tuning. The gap is "manageable" at 400G but becomes "critical" at 800G scale; RoCEv2 fabrics running above ~80% sustained load show amplified tail-latency variance. For ultra-large training clusters where sync-efficiency/latency consistency matters most, IB remains the more predictable choice at scale — which is part of why Azure/OCI (IB) and AWS/GCP (RoCE/EFA) show different tuning postures in §6.

Fault tolerance — don't let a hung rank fail silently

Without async error handling enabled, a hung/failed rank does not raise a clean error — the job just silently stops progressing. This is the single most common way a large training job wastes GPU-hours: everyone assumes it's still running because there's no crash, no traceback, nothing — just no progress.
SettingNotes
NCCL_ASYNC_ERROR_HANDLINGOriginal env var. Deprecated in favor of TORCH_NCCL_ASYNC_ERROR_HANDLING as of PyTorch 2.2.0 — the new var still accepts the old name for backward compatibility.
NCCL_TIMEOUT / PyTorch's timeout=PyTorch's default watchdog timeout is 1800000ms (30 minutes) — this is what produced the "ran for 1803360 milliseconds" message above. Set explicitly rather than relying on the default for production jobs where a faster fail-fast is worth it.

NCCL's own RAS (Reliability/Availability/Serviceability) subsystem (since 2.24) runs a lightweight monitoring thread per process that connects to peers to exchange state, giving a global view of the running job — specifically built to help pinpoint which rank is the outlier/unresponsive one during a hang, rather than staring at N different rank logs individually. Pairs well with PyTorch's own Flight Recorder, which logs start/end/enqueue timestamps and stack traces per collective op for post-mortem hang analysis.

Real-world cost of this at scale — Meta's Llama 3 herd paper (arXiv:2407.21783) reports 466 job interruptions over a 54-day, 16,384-H100 pretraining run (47 planned, 419 unexpected — roughly one unexpected failure every ~3 hours). 78% of unexpected interruptions were confirmed/suspected hardware issues (GPU failures including NVLink, plus HBM3 memory failures, made up the largest share). Despite that failure rate, they held >90% effective training time — attributed to frequent checkpointing (minimizing lost work per restart) and heavy automation (manual intervention needed only 3 times in 54 days). This is the direct operational payoff of getting fault tolerance + fast detection right: a hung/failed rank costs you the time-to-detect (bounded by your timeout setting) plus the time-to-restart-from-checkpoint, not the whole job.

12. Framework Integration, NCCL C API & Profiling

How training frameworks actually call NCCL

Everything in §4-§5 benchmarks NCCL in isolation via nccl-tests — here's how that connects to what a real training job experiences. In PyTorch, torch.distributed.init_process_group(backend="nccl") is the entry point; every subsequent collective call (`all_reduce`, `all_gather`, etc.) on a process group backed by NCCL maps directly onto the same NCCL collectives this page benchmarks. Critically, NCCL's own timeout/error-detection only takes effect when async error handling is enabled (see §10) — without it, PyTorch's `ProcessGroupNCCL` doesn't proactively surface async NCCL errors, which is exactly the silent-hang failure mode described above.

NCCL C API essentials — what's actually underneath nccl-tests and PyTorch

If you ever integrate NCCL directly (not through PyTorch), this is the core call sequence. Every collective in §4 maps 1:1 onto one of these calls.

CallWhat it does
ncclGetUniqueId(ncclUniqueId* id)Called once, by rank 0. Generates an opaque ID that must be distributed to every other rank via an out-of-band mechanism (typically MPI_Bcast, or a socket/file-based exchange) before anyone calls ncclCommInitRank.
ncclCommInitRank(ncclComm_t* comm, int nranks, ncclUniqueId id, int rank)Creates the communicator. Implicitly synchronizes with other ranks — if a single thread manages multiple devices/ranks, this call must be wrapped in ncclGroupStart/ncclGroupEnd.
ncclAllReduce(sendbuff, recvbuff, count, datatype, op, comm, stream)The exact signature shape shared by ncclAllGather, ncclBroadcast, ncclReduce, ncclReduceScatter — buffer pointers, element count, datatype, comm handle, CUDA stream.
ncclSend(sendbuff, count, datatype, peer, comm, stream) / ncclRecv(...)Point-to-point. The receiving rank must post a matching ncclRecv. All-to-all-style patterns built from send/recv loops require ncclGroupStart/ncclGroupEnd around them — without it, each call blocks waiting for its peer to post the matching op, which deadlocks.
ncclGroupStart() / ncclGroupEnd()Batches enqueued NCCL calls — ncclGroupStart defers posting until ncclGroupEnd, which then waits for the whole batch. Required whenever one thread manages multiple devices.
ncclCommDestroy(comm)Graceful teardown — waits for pending ops to complete first.
ncclCommAbort(comm)Immediate termination, cancels in-flight ops. This is the recommended path for error recovery — the mechanism underneath the fault-tolerance material in §10.

Stream semantics: every collective is enqueued on a cudaStream_t — asynchronous and non-blocking on the host by default; completion is a stream event, not a blocking host call. Source: NCCL communicator API docs, NCCL group calls docs.

Profiling NCCL communication

The NCCL Profiler plugin API (introduced alongside PAT in 2.23) provides start/stop event callbacks so external tools can track async NCCL operations. Important caveat: Nsight Systems can trace NCCL activity on the CPU-side timeline (kernel launches, API calls), but it cannot capture the actual GPU-to-GPU communication itself — NCCL uses direct memory load/store between GPUs, not `cudaMemcpy`, so there's no discrete "copy" event for a profiler to hook. If you're trying to see fabric-level communication detail, Nsight alone won't show it; you need NCCL's own instrumentation (`NCCL_DEBUG=INFO`, the Profiler plugin, or vendor-specific telemetry like NVIDIA Spectrum-X's NCCL plugin "NetInspector").

1. What is HPL, and why does it matter?

HPL (High-Performance Linpack) traces back to the LINPACK software package created in the 1970s-80s by Jack Dongarra and colleagues at Argonne National Laboratory / University of Tennessee. HPL, the modern parallel variant introduced in the 1990s, generates a dense n×n linear system Ax=b, solves it via LU factorization with partial row pivoting followed by triangular solves — roughly (2/3)N³ FLOPs total.

Why it's important

  • The TOP500 standard — HPL has ranked the world's fastest supercomputers since 1993. Every major system's public reputation rests on this one number.
  • Full-system stress test — sustaining near-peak FLOPS across an entire cluster for an extended run stresses power delivery, cooling, and interconnect simultaneously. A cluster that can't hold near-peak HPL performance for the full run duration usually has a real hardware or power/thermal issue — which is exactly why it's still used for GPU cluster acceptance testing today, criticism notwithstanding.
  • Widely criticized, still standard — HPL is almost purely compute-bound and doesn't reflect real HPC/AI application performance well (this criticism is exactly why HPCG was created — see §4). Despite that, it remains the universal reference point because it's been consistent since 1993.

What it's used for

  • TOP500 list submissions (public bragging rights + procurement validation)
  • New GPU cluster acceptance testing — proving a cluster sustains near-peak FLOPS at full scale before handoff
  • Power/cooling/interconnect stress testing under sustained maximal load
  • Customer validation deliverables — real-world runs are used as procurement/acceptance evidence

2. How it runs (algorithm)

HPL processes the matrix in panels: each step does a panel factorization (LU decomposition of a column block) followed by a trailing matrix update (applying that transformation to the remaining unfactored submatrix via large GEMM operations). The trailing-matrix-update dominates and is O(n³) FLOPs against O(n²) data movement — high arithmetic intensity is exactly why HPL can sustain a large fraction of theoretical peak, unlike memory-bound codes (contrast with HPCG, §4).

NVIDIA's GPU-accelerated HPL is distributed via the nvcr.io/nvidia/hpc-benchmarks NGC container. GPUs handle the compute-heavy trailing matrix update (large GEMMs); CPUs typically handle panel factorization and pivoting logistics — the split is tuned via NB (§3). Source: glennklockwood.com HPL, NVIDIA HPL Benchmark docs.

5. How results are measured

Rmax

Achieved performance (measured, in FLOP/s) — the official TOP500 ranking number.

Rpeak

Theoretical peak performance of the full system (sum of every core/GPU's peak FP64 FLOPS).

Nmax

The problem size (N) used to achieve Rmax.

Efficiency = Rmax / Rpeak (as a percentage) is the standard way to judge how well a system/tuning realizes its theoretical potential. Typical "well-tuned" GPU cluster efficiency is cited in the 78-90% range across several sources — but real published flagship numbers (§6) often land lower than that, so treat 78-90% as an upper-bound aspiration, not a guarantee.

1. What is MLPerf, and why does it matter?

MLPerf is run by MLCommons (founded 2020, evolved from the original MLPerf effort at Baidu/Google/Harvard/Stanford). It's fundamentally different from HPL/HPCG (§ elsewhere on this site): instead of a synthetic linear-algebra or memory-bandwidth workload, MLPerf measures actual model training-to-a-quality-target or actual model serving under realistic latency/throughput constraints. Two suites: MLPerf Training (wall-clock time to train to a specific quality target — not full convergence) and MLPerf Inference (throughput/latency under defined serving scenarios).

Why it matters

  • NVIDIA's real competitive battleground — AMD, Google, Intel, and every major system vendor publish results in the same rounds, on the same rules, unlike vendor marketing slides.
  • Real workloads, not synthetic FLOPS — HPL tells you peak compute; MLPerf tells you what a real LLM pretraining or serving job actually achieves on that hardware.
  • Strict, auditable rules — the Closed division locks the model/optimizer/hyperparameter space so results are a fair hardware+software-stack comparison, not different teams solving different problems.

What it's used for

  • Public competitive benchmarking (NVIDIA's MLPerf blog posts are a recurring marketing + engineering credibility event)
  • Procurement decisions — buyers use MLPerf results as a trusted, standardized comparison point

MLPerf Power uses the industry-standard SPEC PTDaemon interface (a third-party power analyzer, separate director machine, "dynamic ranging" for precision) — introduced in Inference v1.0 (2021), still the methodology today.

1. What is gpu-burn, and why does it matter?

gpu-burn (github.com/wilicc/gpu-burn, 2.3k stars, BSD-2-Clause) is Ville Timonen's original GPU stress-test tool — wilicc on GitHub is the original author, this is not a third-party fork. Released 2013. It forks one process per GPU, allocates a high percentage of GPU memory, and runs continuous cuBLAS matrix multiplications for a specified duration — while periodically validating results against a reference computation to catch silent data corruption (SDC), not just "does it run."

Why it matters

  • Pre-deployment burn-in — catches thermal throttling, marginal power delivery, and unstable/defective cards before they enter production.
  • Catches silent data corruption — a GPU that runs hot but computes wrong answers is worse than one that visibly crashes; gpu-burn's correctness check is what catches this.
  • A real production workflow, not just a one-time test — commonly run on a regular cadence and before returning repaired nodes to service.

Where it fits alongside NCCL & HPL

  • gpu-burn — single/multi-GPU compute + thermal + correctness stress (this page)
  • NCCL tests — interconnect/fabric health (ring/tree AllReduce busbw)
  • HPL — full-system sustained FLOPS at scale (power/cooling/interconnect combined)
  • Different scope, same goal: prove the hardware is production-ready before it's trusted with real workloads.

2. How it runs

Default precision is double (DGEMM) via -d — heavier thermal/power load, closer to worst-case realistic stress than single-precision. Runs on all visible GPUs simultaneously by default; -i N narrows to one GPU.

1. What are these, and why do they matter together?

2. GPU acceleration approach

LAMMPS

Two competing packages: GPU package (partial offload — pairwise force calc only) vs. KOKKOS package (whole simulation on GPU, minimizes host↔device transfer). Real finding: Kokkos "outscales the GPU package because it minimizes host-to-GPU data transfer" (ACES cluster study, H100 vs Intel Data Center GPU Max 1100). CPU-GPU ratio: 16-32 CPU cores per GPU.

GROMACS

Native CUDA/SYCL/OpenCL. Default hybrid scheme still runs PME and bonded forces on CPU — full offload requires explicit flags (-nb gpu -pme gpu -bonded gpu -update gpu), which "pins threads to host CPU."

NAMD

GPU-resident mode (NAMD 3.0+) keeps simulation data on-device between timesteps, eliminating per-step host-device communication — claimed >2× performance gain over the earlier GPU-offload mode, up to 7× on supported hardware (DGX) vs. the old mode.

Universal bottleneck across all three: PME/electrostatics (particle-mesh Ewald) — usually the hardest part to offload efficiently and the first thing to check when GPU scaling disappoints.

1. What is GPUDirect Storage, and why does it matter?

GPUDirect Storage (GDS) gives GPUs a direct DMA data path to/from storage, bypassing the CPU "bounce buffer" that traditional I/O requires (storage → CPU RAM → cudaMemcpy → GPU memory). Part of NVIDIA's Magnum IO suite.

Why it matters

  • Checkpoint save/load at scale — multi-hundred-GB checkpoints are common at frontier model scale; every minute spent loading is a minute of idle, expensive GPU time.
  • Dataset streaming — data-hungry training jobs stall waiting for the next batch if the I/O path can't keep up with GPU compute.
  • Real, dramatic, sourced impact: a 140GB checkpoint load dropped from 4-5 minutes to under 40 seconds. Llama 3.1 405B model load (via FSx for Lustre + GDS + pre-sharded/pre-quantized checkpoints): 10-20 minutes → 6 seconds.

Real-world case study

Meta reported a 3.8× training speed improvement from GDS adoption: 192GB/s direct-to-GPU throughput vs. 50GB/s CPU-bottlenecked — and data-loading dropped from 35% to 5% of total training time.

Sources: Spheron GDS guide, AWS FSx for Lustre + GDS blog.

2. How it runs (architecture)

User-level library libcufile.so + kernel driver nvidia-fs.ko. Core calls: cuFileRead/cuFileWrite — mirror POSIX pread/pwrite but take GPU virtual addresses directly. Filesystem-agnostic — GDS-certified storage: DDN EXAScaler, WekaFS, VAST (NFS), IBM Spectrum Scale, NetApp ONTAP, BeeGFS, Dell EMC Isilon, Micron. Each vendor implements GDS callback hooks into nvidia-fs.ko.

Source: GDS Overview Guide.

4. The silent fallback trap

This is the same failure-mode pattern already documented for GPUDirect RDMA on the NCCL page: GDS can silently fall back to the traditional POSIX path with no error message, and a job just... runs slower. Always verify with gdscheck rather than assuming GDS is active because the job completed.

Compatibility-mode fallback triggers on: missing nvidia-fs.ko, unsupported filesystem, file not opened with O_DIRECT, or unaligned buffers/offsets/sizes (must be 4K-aligned). One vendor-specific gotcha: WekaFS always falls back to POSIX for writes specifically (reads are GDS-accelerated, writes are not) — worth knowing if you're benchmarking on Weka and see asymmetric read/write numbers.

Source: GDS Troubleshooting Guide.

8. How to run it

  1. Verify GDS is actually active: /usr/local/cuda-<x>.<y>/gds/tools/gdscheck.py -p — reports which mounted filesystems have GDS active + PCIe ACS switch status.
  2. Configure /etc/cufile.json (buffer sizes, allow_compat_mode).
  3. Benchmark: gdsio -D <path> -d <gpu> -w <threads> -s <size> -i <io_size> -x <xfer_type> -I <op> -T <seconds>
  4. Debug: CUFILE_LOGGING_LEVEL=TRACE, check /proc/driver/nvidia-fs/stats (watch Registered_MB/Cache_MB), and cufile.log.
Common pitfall: wrong filesystem type or a missing O_DIRECT flag silently degrades to POSIX compat mode with no error — always confirm via gdscheck rather than assuming GDS is active just because the job ran.

1. What is this, and why does it matter?

"Open-weight" doesn't mean one thing — licenses range from truly permissive (Apache 2.0, MIT) to gated/custom terms with usage caps. This page tracks the major families people actually deploy against each other: what they cost to run, what license risk they carry, and how they're architected (dense vs. Mixture-of-Experts).

Benchmark numbers in the open-model space move fast and are frequently gamed (see the Llama 4 Maverick LMArena controversy in §5). Treat any single leaderboard number as a snapshot, not gospel — cross-check against the primary source (official model card / official leaderboard site) before using a number to make a real decision.

4. Architecture: dense vs. Mixture-of-Experts (MoE)

Dense

Every parameter activates on every forward pass. Simpler to serve, more predictable latency, but total params = active params = full compute cost. Examples: Gemma 3, Phi-4, OLMo 3, Qwen3 dense variants (32B/8B/4B/0.6B).

MoE

Only a subset of "expert" sub-networks activate per token — total params can be huge while active (compute) params stay small. Examples: DeepSeek-V3 (671B total/37B active), Llama 4 Maverick (400B/17B), GLM-5 (744B/40B), Mistral Large 3 (675B/~40B). This is why a 671B MoE model can be cheaper to run than its total-param count implies — but still needs enough GPU memory to hold all the experts, even though only a few fire per token.

The trend across 2025-2026: nearly every new frontier-scale open-weight release is MoE — it's become the default way to get more model capacity without proportionally more inference compute.

5. Cross-family leaderboards — and their limits

  • LMArena (LMSYS Chatbot Arena) — live Elo-based rankings from human pairwise votes. As of ~Sept 2026, proprietary models (Claude Opus, GPT-5.5 Pro, Gemini 3.1 Pro) still dominate the top overall, but open-weight Kimi K3 broke into #1 on the Frontend Code Arena sub-leaderboard specifically.
  • Artificial Analysis — Intelligence Index scoring across quality/speed/price. GLM-5.3-Flash and Kimi K3 rank near the top among open models per secondary reporting — pull live numbers directly from the site before quoting, since aggregator blogs can lag or misreport.
  • Hugging Face Open LLM Leaderboard — historically the standard reference; HF has changed/retired leaderboard formats before, so confirm it's still actively maintained before citing.
The Llama 4 Maverick episode is the cautionary tale here: Meta's submitted "03-26-Experimental" variant scored 1417 Elo (would-be top-tier), but the actual publicly released weights ranked around 32nd once LMArena applied style control — the submitted variant was tuned for benchmark performance, not representative of the shipped model. Always check whether a benchmark number was measured on the model you can actually download.

6. How to choose, practically

License-sensitive deployment

Favor Qwen3, DeepSeek, GLM-5.x, Mistral Large 3, Grok-1, Phi-4, or OLMo 3 — all Apache 2.0/MIT with no usage-count gates.

Memory-constrained serving

MoE models need enough GPU memory to hold ALL experts even if only a few fire per token — a 671B-total MoE model still needs multi-GPU memory footprint despite ~37B active compute. Dense small models (Gemma, Phi-4, Qwen3 dense) are simpler to reason about for tight memory budgets.

Full transparency / research use

OLMo 3 is the only family here shipping pretraining data + full training code + logs alongside weights — the closest thing to a fully reproducible open model.
